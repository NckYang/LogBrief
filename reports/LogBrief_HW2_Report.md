# LogBrief：保留錯誤證據的日誌壓縮與 MCP 工具

姓名：楊竣凱　學號：112502039

HW2：AI-Assisted Programming Project　｜　更新日期：2026-11-01

LogBrief 將冗長的 Python 日誌轉換成附原始行號、符合本機 token 預算的除錯證據，供 LLM agent 分析。在隨附的 342 行合成案例中，完整提示詞由 4,429 降至 526 tokens，減少 88.12%，同時保留欄位資訊、第一個錯誤與完整 traceback。專案提供 CLI、Python API 與標準 stdio MCP，將日誌整理做成可重現、可查證、可供 agent 重用的軟體元件。

## 1. Purpose

### 1.1 問題背景與使用情境

在訓練模型、處理資料或執行 Python 程式時，一次失敗可能留下數百行進度訊息與重複警告。使用者需要找出錯誤位置、相關設定與前後文，再交給 LLM 協助除錯。完整貼上日誌會占用輸入空間；只貼最後幾行，則可能遺失較早的資料欄位或設定資訊。

本專案面向需要分析這類日誌的學生、研究者與開發者。目標是讓使用者提供原始日誌與輸入預算後，即可取得較精簡、能回查來源的證據，減少手動整理的負擔，並讓 agent 的分析建立在可核對的內容上。

### 1.2 核心設計與專案價值

| 使用者需求 | LogBrief 的設計 | 實際價值 |
|---|---|---|
| 重複訊息占用輸入 | 合併重複進度與相同警告，保留次數及來源範圍 | 縮短輸入，同時保留事件頻率與進度概況 |
| 壓縮可能刪掉線索 | 保護可辨識的完整 Python traceback、第一個錯誤與前後文 | 保留追查失敗位置所需的基本證據 |
| 模型回答需要查證 | 證據附原始行號，JSON 記錄選取與省略資訊 | 使用者能回到原始日誌核對回答 |
| 輸入長度受限 | 將提示詞與預留量納入本機 token 計數 | 預算不足時明確回報，避免默默截斷必要證據 |
| 工具需整合既有流程 | CLI、Python API 與 MCP 共用壓縮核心 | 可從人工操作逐步整合至 agent 工作流程 |

與直接截取尾端相比，LogBrief 另會選取設定與指標變化等候選線索；與直接要求 LLM 摘要相比，壓縮階段採固定規則，不需額外呼叫模型。這些設計提供可檢查的選取依據，但不保證保留每一條具有因果關係的資訊。

本專案的驗收重點是預算內輸出、必要錯誤區段完整、來源行號可追溯，以及 agent 可透過標準工具介面呼叫。診斷準確率、費用與時間的普遍改善，則需要額外實驗才能成立。

## 3. How I Integrate Software Engineering Practice into My Product

### 3.1 模組化架構與處理流程

```text
使用者 / agent
      ↓ CLI、Python API 或 MCP compress_log
讀取日誌 → 解析原始行號 → 辨識並保護錯誤區段
      → 合併重複事件 → 依優先序選取其他線索
      → 重新核對 token 預算 → 輸出證據與統計
                                    ↓
                         agent 診斷 → 使用者回查與驗證
```

| 模組 | 職責 | 工程上的意義 |
|---|---|---|
| logbrief/compressor.py | 解析日誌、保護區段、摘要分組與預算選取 | 核心邏輯集中，供不同介面重用 |
| logbrief/tokens.py | tokenizer 與 token 計數 | 長度衡量與壓縮規則分離 |
| logbrief/prompts.py | 診斷提示詞與證據格式 | 要求引用來源、區分觀察與推測 |
| logbrief/cli.py | 命令列、文字及 JSON 輸出 | 方便人工重現與批次處理 |
| logbrief/mcp_server.py | stdio MCP、輸入驗證與工具回傳 | 讓 agent 透過標準介面使用相同能力 |

壓縮先放入不可分割的必要證據，再依優先序加入警告、設定、指標與一般訊息。最後重新計算完整提示詞；若超出預算，只移除可選內容。若必要證據本身已超過預算，則回報 BudgetTooSmall，要求提高預算。這項取捨讓成功輸出不會以截斷受保護區段為代價。

進度分組僅正規化進度計數等資訊，不將不同 loss、accuracy 數值直接當成相同訊息。Traceback 採保守規則辨識邊界，仍有格式適用範圍，不能視為涵蓋所有語言的解析器。

### 3.2 測試、錯誤處理與可檢查性

原交付紀錄記載 18 個壓縮核心測試通過，並曾透過真正 MCP client 檢查工具探索、成功呼叫、無效輸入與錯誤後繼續使用。本次報告修訂另重新執行目前版本的壓縮示範，確認主要數值與原始行號一致；沒有將歷史測試當成本次重新執行的結果。

| 檢查面向 | 實作行為與目的 |
|---|---|
| 證據完整性 | 保護可辨識 traceback 與錯誤前後文，避免產生看似完整卻缺段的證據 |
| 輸入與預算 | 拒絕空日誌、無效參數及過小預算，讓失敗原因可理解 |
| 檔案操作 | CLI 拒絕覆寫輸入日誌；MCP 檔案路徑限制於指定工作區 |
| MCP 輸入界線 | log_path 與 log_text 擇一；檔案限定 UTF-8 的 .log／.txt，輸入最多 1,000,000 bytes |
| 模型使用規範 | 提示詞要求將日誌視為不可信資料、引用行號，且不得宣稱已執行修復 |
| 結果檢查 | CLI JSON 提供預算、受保護行、分組與省略資訊；MCP 回傳精簡證據、統計與 traceback 範圍 |

## 4. Result

### 4.1 可重現的量化結果

輸入為 examples/training.log：342 行人工合成 Python 訓練日誌，含 300 筆進度、30 筆相同警告及 KeyError。設定為 cl100k_base、token 預算 1,200、前後文 3 筆與預留量 32。本次於 2026-11-01 重跑壓縮示範，結果如下。固定結果快照見 reports/evidence/current_demo_report.json；各項證據的來源與重現限制見 reports/evidence/README.md。

| 指標 | 結果 | 解讀 |
|---|---|---|
| 完整提示詞 → 壓縮提示詞 | 4,429 → 526 tokens | 相同本機計數口徑，含 system／user 文字及預留量 |
| 提示詞縮減率 | 88.12% | (1 − 526 ÷ 4,429) × 100%；不能直接等同 API 費用減少比例 |
| 預算使用 | 526／1,200，約 43.83% | 此案例在本機設定預算內完成 |
| 錯誤與 traceback | L335；L336–L341 | 第一個錯誤與完整 traceback 保留 |
| 受保護區段 | L332–L342，共 11 筆 | 保留資料欄位、例外位置與終止狀態 |
| 重複事件 | 300 筆進度、30 筆警告形成摘要 | 保留次數及來源範圍 |

JSON 中 omitted_records = 0 表示每筆事件均有原文或群組摘要代表，不表示每一行原文皆逐字保留。群組次數也包含受保護區段中的重複原文，不能再把原文出現次數加上去。

### 4.2 從證據到診斷的具體案例

| 保留的來源 | 可支持的判斷 |
|---|---|
| L334：Available columns: feature_1, feature_2, target | 可用欄位清單中沒有 label |
| L335：Requested label column 'label' does not exist | 程式明確回報所需欄位不存在 |
| L339–L341：train.py 第 18 行、frame["label"]、KeyError | 將錯誤連結至實際欄位存取位置 |
| L342：Training aborted; no model checkpoint was written | 此次訓練中止，未寫入模型 checkpoint |

這組證據連結了資料實際提供的欄位、程式預期的欄位與觸發例外的位置。使用者因此能檢查欄位對應，而不只得到孤立的 KeyError 訊息。至於 target 是否真的是正確標籤，仍需確認資料語意。

歷史 Gemini 實測接收壓縮證據後，辨識出 label 欄位不存在，引用行號，並提出統一欄位名稱及重新執行檢查的建議。附件記錄 API 實際輸入 575 tokens、輸出 663 tokens、生成請求耗時 2.827 秒，回答未截斷。這是既有紀錄，本次沒有重新呼叫模型；該耗時也不是壓縮前後的速度比較。

本機的 526 與 Gemini 的 575 採不同 tokenizer／計數範圍，不能直接混用。實測支持此案例壓縮後仍足以辨識核心錯誤，但未證明壓縮提升整體準確率，也未實際執行模型建議的修復。

### 4.3 證據選取的補充觀察

歷史選取比較 reports/evidence/selection_ablation.json 記錄三個案例。在 metric_instability 案例中，固定優先序未呈現指定的 L80–L82，改善後三行皆被呈現；distant_configuration 與 multiple_failures 兩案則是兩種方式均保留指定行。該 JSON 僅保存選取結果摘要，精簡 repo 未包含原比較程式與完整案例輸入，因此不能只憑此檔重現比較。這提供了加入指標線索的具體理由，但僅是歷史選取結果，不是診斷準確率評測，也不是目前版本的新一輪基準測試。

### 4.4 助教重現與 MCP 展示方式

在 Python 3.11 以上的環境，於專案根目錄執行：

```powershell
python -m pip install -e ".[mcp]"
python -m examples.compression_demo
```

輸出 outputs/compressed.txt 與 outputs/report.json。可先核對 4,429 → 526 tokens，再對照 examples/training.log 的 L334–L341，確認欄位資訊與完整 traceback 均在壓縮結果內。

MCP 展示：在支援 stdio MCP 的 agent 設定 command 為 python、arguments 為 ["-m", "logbrief.mcp_server"]，使用安裝本套件的 Python 環境。呼叫 compress_log 的參數範例如下：

```json
{"log_path": "examples/training.log", "token_budget": 1200}
```

讓 agent 根據回傳 evidence 說明原因、修復方向與驗證步驟，並引用原始行號。此設計對應作業的 MCP 加分項目：agent 可實際呼叫專案能力，壓縮由本機工具完成，診斷由呼叫端模型負責。MCP 的 token 統計不包含宿主 agent 的完整對話、工具封裝與其他上下文，不能當作整個 agent 請求的硬上限。

### 4.5 限制、後續方向與專案貢獻

目前主要量化成果來自單一合成案例，重複訊息比例高；短日誌可能因加入行號及摘要標記而沒有壓縮收益。規則式選取也可能省略尚未辨識的重要前因，尤其是非 Python 格式、跨服務事件與不明確的 traceback 邊界。提示詞要求引用證據，有助於核對，但不保證模型一定遵守。

後續優先工作是將核心回歸測試納入 repo 與 CI，再使用更多真實日誌，比較完整輸入、尾端截取與 LogBrief。在相同計數口徑下衡量 token 用量、已知關鍵證據保留率、診斷正確性及端到端耗時，並記錄失敗與無壓縮收益的案例。

本專案完成了一個可供 agent 呼叫的日誌證據整理元件，將預算控制、錯誤保護、來源追溯與介面整合放入同一套可重現流程。現有成果展示了：對大量重複的 Python 日誌，可以大幅縮短輸入，同時留下足以核對此案例診斷的證據；清楚界定尚未驗證的效果，也讓後續改進有具體依據。
